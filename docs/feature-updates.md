「できるようになったこと」を知らないまま契約しているお客様が多いため、週に1回まとめてお知らせする。

- 台帳：`shared/featureUpdates.ts` の `FEATURE_UPDATES`
- 仕組み：`server/featureUpdates.ts`（毎週水曜 11:30 JST・`server/dailyOpsJobs.ts` の `30 2 * * 3`）
- 記録：`featureUpdateItems`（項目ごとの状態）・`featureUpdateDeliveries`（お一人ずつの配信記録・(itemId, userId) 一意）。マイグレーション `drizzle/0113_feature_updates.sql`
- 試験：`server/featureUpdates.test.ts`・`server/featureUpdatesLedger.test.ts`

## 運用の決まり（必ず守る）

1. **お客様に見える機能を本番に入れ、本番で実際に動いたことを確かめたら、`FEATURE_UPDATES` に1件足す。**
   - `verifiedAt`（確かめた日 YYYY-MM-DD）と `verifiedHow`（何で確かめたか）は**必須**。
   - 確かめるのは「作った」「入れた」「mode=on にした」ではなく、**本番DBに使われて動いた記録があること**（例：その機能から公開された投稿が `status='posted'` で1件以上）。
   - 2026-11-02 の教訓：写真つき自動投稿は 10/28 に mode=on にしたが、本番では mediaItems を使った公開が0件で、一度も動いていなかった。
2. まだ確かめられない機能は、`verifiedAt` を入れずに台帳へ入れてよい（配信されない）。`verifiedHow` に「未確認（日付）：理由」を書き、確かめたら `verifiedAt` を足す。
3. `id` は英数字で、あとから変えない（配信記録のキー）。
4. 文面：2〜4行。何ができるか・どう使うか（LINEのどのボタンを押すか／何を送るか）を、やさしい言葉で書く。
   絵文字なし・「AIが」と書かず「自動で」・講師名・書名・広告費の額は書かない。プランなどで使えない方がいる機能は `when` で絞る（例：写真つきはプロ以上）。
5. このリポジトリは公開。`verifiedHow` にお客様の名前・アカウント名を書かない（件数と日付だけ）。

## 流れ

1. 水曜 11:30：確かめずみで、まだ送っていない（「出さない」とも決めていない）項目を集める。**0件の週は何もしない。**
2. 三上様の公式LINEへ下見：項目の一覧・配信先の人数・お客様に届く文の見え方ごとの全文（多い順に3通りまで）。
   ボタン：「この内容で送る」／「今週は送らない」（来週の下見に持ち越す）／「この項目は出さない」（今後も出さない）。
3. **お客様へは自動で送らない。** 「この内容で送る」を押した時だけ、配信先を数え直して送る。押されなければ、次の週の下見にもう一度入る（6日以内は出し直さない）。
4. 配信先は読み物と同じ（`listNewsletterRecipients`：有料・ご契約中。解約の予約があっても期間内は送る。`newsletterOptOuts` の方には送らない）。LINEがあればLINE、無ければメール。
   お一人ずつ `when` に当てはまる項目だけを1通にまとめる。同じ項目は同じ方へ二度送らない。
